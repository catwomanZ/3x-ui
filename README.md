# 3x-ui روی Railway

**پنل رسمی 3x-ui نسخه `v3.10.2` — با یک پورت، روی یک سرویس Railway**

بدون VPS، بدون دامنه، بدون Cloudflare. لینک ساب می‌گیری، روی گوشی کار می‌کند.

[![Deploy on Railway](https://railway.com/button.svg)](https://railway.com/new)
[![Star on GitHub](https://img.shields.io/github/stars/catwomanZ/3x-ui.3.9.0?style=social)](https://github.com/catwomanZ/3x-ui.3.9.0)

</div>

## ⚡ راه‌اندازی

### ۱. ریپو را فورک کن

دکمه‌ی **Fork** بالای همین صفحه.

### ۲. روی Railway دیپلوی کن

دکمه‌ی بالا → **New Project** → **Deploy from GitHub repo** → ریپوی فورک‌شده.

> دکمه‌ی بالا فقط درِ Railway را باز می‌کند و **ریپو را خودش انتخاب
> نمی‌کند**. برای اینکه تک‌کلیک واقعی شود و ریپو از پیش انتخاب‌شده باشد،
> سازنده باید یک Railway Template منتشر کند (پایین صفحه توضیح داده شده).

### ۳. دو تا چیز را دستی ست کن

این دو را نمی‌شود از داخل کد ست کرد:

| کجا | چه کار |
|---|---|
| **Settings → Volumes → Add volume** | Mount Path را بگذار `/etc/x-ui` |
| **Settings → Networking → Generate Domain** | دامنه‌ی عمومی Railway را بساز |

> **Volume** را نگذاری، هر دیپلوی کلاینت‌ها و رمزت را پاک می‌کند.
> دامنه در اولین باز شدن پنل یا لینک ساب خودکار شناسایی و ذخیره می‌شود؛ اگر
> Railway متغیر دامنه را دیر تزریق کند هم دیگر کانفیگ خالی ساخته نمی‌شود.

### ۴. تمام

لاگ دیپلوی را باز کن. آدرس پنل و لینک ساب همان‌جا چاپ می‌شود:

```
Panel          https://<دامنه‌ی‌تو>.up.railway.app/panel/
Subscription   https://<دامنه‌ی‌تو>.up.railway.app/sub/CATWOMAN
```

## 🔑 ورود

| | |
|---|---|
| **کاربری** | `admin` |
| **رمز** | `admin` |

**اولین کاری که می‌کنی عوض کردن رمز باشد:**
پنل ← تنظیمات پنل ← احرازهویت ← اعتبارنامه‌های ادمین

اگر رمز را فراموش کردی، در Railway Variables فقط `ADMIN_PASSWORD` را با رمز
جدید بگذار و Redeploy کن؛ نام کاربری ذخیره‌شده و همه‌ی کلاینت‌ها حفظ می‌شوند.

## 👥 کاربر اضافه کردن

لازم نیست اینباند بسازی یا لینک تازه بدهی:

1. پنل ← **Clients** ← **Add Client**
2. یک **Email** بده (مثلاً `ali`)
3. در **Sub ID** دقیقاً `CATWOMAN` را بنویس
4. **تیک ورودی را بزن** ← ذخیره

کانفیگش خودش به **همان لینک ساب** اضافه می‌شود. لینک جدیدی در کار نیست.

> ⚠️ دو تا چیز که پنل رد می‌کند:
> - **فاصله** در اسم — `Ali Reza` قبول نمی‌شود، `ali_reza` یا `علیرضا` قبول است
> - **تیک نزدن اینباند** — `at least one inbound is required`

## 🌐 بخش Hosts

در منوی پنل، **Hosts** کنار **Inbounds** در دسترس است. یک ردیف مدیریت‌شده با
نام `CATWOMAN` برای Railway نگه داشته می‌شود و باید این مشخصات را نشان بدهد:

| فیلد | مقدار درست |
|---|---|
| Address | دامنه‌ی عمومی فعلی Railway |
| Port | `443` |
| Security | `tls` |
| SNI | همان دامنه‌ی عمومی |
| Host Header | همان دامنه‌ی عمومی |
| Path | `/ws` |

می‌توانی Hostهای CDN یا دامنه‌ی شخصی خودت را اضافه و ویرایش کنی؛ ردیف‌های
سفارشی دست‌نخورده می‌مانند. ردیف `CATWOMAN` هم تا وقتی تغییرش نداده‌ای با
دامنه‌ی Railway خودکار هماهنگ می‌شود، اما به محض اینکه آن را در بخش Hosts
ویرایش و Save کنی، تغییر دستی تشخیص داده می‌شود و دیگر درخواست بعدی پنل آن را
برنمی‌گرداند. برای فعال‌کردن دوبارهٔ حالت خودکار، ردیف `CATWOMAN` را حذف و
پنل را یک بار باز کن تا با تنظیمات استاندارد دوباره ساخته شود.

این تغییرات داخل `/etc/x-ui/x-ui.db` هستند؛ بدون Volume روی `/etc/x-ui` فقط تا
Restart یا Redeploy بعدی باقی می‌مانند.

## 📱 لینک

این را بده به هر کسی که می‌خواهد وصل شود:

```
https://<دامنه‌ی‌تو>.up.railway.app/sub/CATWOMAN
```

در **مرورگر** باز کنی، صفحه‌ی ساب می‌آید. در **v2rayNG / Streisand / v2box**
وارد کنی، کانفیگ خام می‌گیرد. یک آدرس، دو رفتار — خود پنل تشخیص می‌دهد چه
کسی دارد می‌پرسد.

اگر فرمت‌های JSON یا Clash/Mihomo را در تنظیمات Subscription روشن کنی، مسیرهای
عمومی ثابت آن‌ها هم آماده‌اند:

```text
https://<دامنه‌ی‌تو>.up.railway.app/sub-json/CATWOMAN
https://<دامنه‌ی‌تو>.up.railway.app/sub-clash/CATWOMAN
```

هر سه فرمت از دامنه‌ی عمومی، `443`، TLS، SNI/Host درست و مسیر `/ws` استفاده
می‌کنند و هیچ‌کدام پورت داخلی `10085` یا `2096` را نشان نمی‌دهند.

---

## ⚠️ اگه کار نکرد

| مشکل | علت |
|---|---|
| کانفیگ دامنه‌ی قدیمی دارد | یک بار پنل یا `/sub/CATWOMAN` را با دامنه‌ی جدید باز کن |
| داخل کانفیگ `10085` یا `2096` می‌بینی | نسخه‌ی قدیمی در حال اجراست؛ از GitHub **Redeploy** کن و دوباره ساب را بگیر |
| بخش **Hosts** را نمی‌بینی | یک بار Hard Refresh بزن؛ اگر برنگشت، دیپلوی باید `v3.10.2` باشد |
| تغییرات **Hosts** فوراً برمی‌گردد | آخرین نسخه را Redeploy کن؛ نسخهٔ جدید ویرایش دستی ردیف `CATWOMAN` را حفظ می‌کند |
| هر دیپلوی کلاینت‌ها یا Hostها می‌پرد | **Volume** با مسیر `/etc/x-ui` اضافه نکردی |
| صفحه‌ی ساب باز نمی‌شود | دامنه‌ی Railway و وضعیت Deploy را چک کن؛ لینک درست `/sub/CATWOMAN` است |
| کلاینت «منقضی» نشان داده می‌شود | تاریخ انقضا را دوباره ست کن؛ `TZ` پیش‌فرض `Asia/Tehran` است |

## 🎨 برند

اسم برند پیش‌فرض `CATWOMAN` است. برای عوض کردنش، در Railway Variables:

```
BRAND=اسم_خودت
```

همین. عنوان تب، صفحه‌ی ورود، سایدبار، اسم ورودی و اسم کانفیگ‌ها همه عوض
می‌شوند. **فونت و چیدمان دست نمی‌خورد.**

متن‌های صفحه‌ی ساب هم قابل تغییرند:

| متغیر | پیش‌فرض |
|---|---|
| `SUB_TITLE` | `CATWOMAN` |
| `SUB_ANNOUNCE` | `این پنل توسط Catwoman ساخته شده` |
| `SUB_SUPPORT_URL` | `t.me/Catwoman_ZaHra` |

بقیه‌ی متغیرها (`PANEL_PATH`، `TUNNEL_PATH`، `TRANSPORT`، `TZ` و…) همگی
پیش‌فرضِ کار‌کننده دارند — دست‌زدن بهشان لازم نیست.

## 🧩 چه چیزی داخلش هست

Railway به هر سرویس **یک پورت** می‌دهد و TLS را خودش در لبه انجام می‌دهد.
پنل ۲۰۵۳ می‌خواهد، سرویس ساب ۲۰۹۶ و Xray پورت خودش را — این پورت‌ها داخل
کانتینر می‌مانند و فقط `$PORT` از Railway به اینترنت باز است. nginx بر اساس
مسیر URL آن‌ها را جدا می‌کند:

```
client ──https──▶ Railway edge (TLS) ──http──▶ nginx :$PORT
   ├─ /healthz            → 200
   ├─ /panel/…            → پنل        :2053
   ├─ /sub/…              → ساب خام    :2097 ─▶ :2096
   ├─ /sub-json/…         → ساب JSON   :2097 ─▶ :2096
   ├─ /sub-clash/…        → Clash      :2097 ─▶ :2096
   ├─ /ws                 → Xray       :10085
   └─ /                   → 404
```

| فایل | کار |
|---|---|
| `Dockerfile` | Ubuntu + باینری رسمی `x-ui v3.10.2` + nginx |
| `entrypoint.sh` | مهاجرت امن دیتابیس، تنظیم‌ها، ساخت اینباند و اجرای سرویس‌ها |
| `public_endpoint.py` | هماهنگ‌کردن Host مدیریت‌شده، SNI، WS Host و لینک ساب |
| `nginx.conf.template` | تفکیک مسیرها، کشف دامنه و حفظ برند پنل |
| `subserver.py` | کشف دامنه از درخواست واقعی و سازگار کردن هدرها با اپ‌ها |
| `railway.json` | healthcheck و سیاست ری‌استارت |

دیتابیس `v3.9.0` روی همان Volume به `v3.10.2` مهاجرت می‌کند و کاربرها،
کلاینت‌ها، اینباندها و Hostهای سفارشی حفظ می‌شوند. خروجی مدیریت‌شده‌ی Railway
همیشه دامنه‌ی عمومی، پورت `443`، `TLS`، SNI و WS Host یکسان و مسیر `/ws`
دارد؛ پورت‌های داخلی `10085` و `2096` وارد کانفیگ کاربر نمی‌شوند.

**نکته:** صفحه‌ی ساب **همان صفحه‌ی پیش‌فرض خود 3x-ui است**، نه یک صفحه‌ی
دستی‌ساز. فقط سه فیلد برند رویش می‌نشیند.

**نکته‌ی دوم:** وقتی کلاینت سقف حجم ندارد، 3x-ui هدر `Subscription-Userinfo`
را با `total=0` می‌فرستد (`internal/sub/calendar_expire.go` هیچ شرطی ندارد).
v2box با این هدر «شکست» می‌زد، با اینکه خود کانفیگ‌ها سالم رسیده بودند.
forwarder آن هدر را در این حالت نمی‌فرستد. سقف حجم که بگذاری، هدر با عدد
واقعی برمی‌گردد.

## 🔧 برای نگهدارنده: تک‌کلیک واقعی کردن دکمه

دکمه‌ی Deploy برای اینکه ریپو را از پیش انتخاب‌شده باز کند، به یک **کد
template** نیاز دارد. آن کد فقط از اکانت Railway سازنده ساخته می‌شود:

1. پروژه را یک بار کامل بالا بیاور (Volume و Generate Domain ست شده باشد)
2. در Railway: سرویس ← **⋮** ← **Generate Template**
3. Template را **Publish** کن
4. لینکی مثل `railway.com/new/template/AbCdEf` می‌گیری — همان `AbCdEf` کد است
5. در خط دکمه‌ی بالای README، `https://railway.com/new` را با
   `https://railway.com/new/template/AbCdEf` عوض کن
